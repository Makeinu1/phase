# Phase Fork 運営契約

版 1.1 — 2026-09-30

この契約は Phase Fork の作業手順と判断境界を揃え、運営上の学びを次の作業へ反映する。大方針とマイルストーンは [Fork ロードマップ](fork-roadmap.md) を参照する。1 iteration は1つの bounded task とする。複数の独立 slice は並行できるが、固定のレーン数や担当数は設けない。Phase の製品・コードの正本は引き続き各 Issue とリポジトリの設計資料に置く。この文書は包括的な作業権限や、upstream への変更許可を追加しない。

## 製品と役割

- 製品は Phase。OneDeck は要求と触り心地を言語化したモックであり、その実装を Phase へ移植する指示ではない。
- 目標は汎用的な致命的進行バグの解消、Cloudflare 無料枠での運用、モック M0〜M6 で示した製品要求の Phase への反映。
- ユーザーは触り心地と方向性を判断する。ラプラスくんは技術方針、優先順位、作業分割、配分、完了判定を担う。体験や方向性を変える判断はユーザーに相談する。

## タスクの流れ

1. ChatGPT が GitHub を調査し、短い Fork Issue を作成する。独立レビューを行う。
2. Luna が Issue を読み、Fork 上で実装と必要な検証を行う。
3. 十分に仕上がり、独立検証が通った後に、Luna が upstream PR または更新を行う。
4. ラプラスくんはメール/GitHub 通知を契機に実物を確認し、次のタスクを配分する。
5. マージの判断と実行は Phase オーナーが行う。助手は merge や auto-merge を行わない。
6. 本家へのマージを確認した後、post-merge 検証とローカル整理までをタスクとして閉じる。

Issue を実装指示の正本とし、目的、症状と根拠、対象と除外、受入れ条件、候補 SHA と検証、次の一手を簡潔に書く。履歴の長い再注入、調査の重複、新 framework や大量文書の追加を避ける。レビューは変更箇所を中心に行い、重大な設計変更が必要な場合に再設計する。

複数の境界不具合を調べるときは、局所実装の前に共通原因と似た症状を区別し、個別修正と上位契約の変更案を比較する。各案が解消する Issue と残余、移行・互換性・公式ルールへの影響、全体の複雑さと保守負担を示し、変更行数ではなく全体負担を小さくする案を証拠とトレードオフとともに Phase オーナーへ提示して判断を仰ぐ。これは調査と判断の基準であり、新 framework の構築やゲームルール変更を許可するものではない。

## 並行作業と証拠

- maintainer 待ちの候補は凍結し、Luna の作業を消費させずに独立した slice を進める。
- 独立した作業は branch、worktree、Luna、ChatGPT スレッドを分けて並行できる。同じ候補には writer を一人だけ置き、責務が重なる作業は順序を調整する。
- Luna には意味のまとまり単位で委任し、合意範囲を自律的に仕上げてもらう。操作ごとのPRO承認往復を求めず、通常の実装判断は委任先に任せる。設計例外や体験・方向性を変える判断を戻して相談する。
- 既存タスクを再利用し、古い完了報告を現在の HEAD の証拠として扱わない。
- 公開前に exact SHA、diff、integration base、tests/gates、scope を独立検証する。CI green だけで完了としない。差分が変わったら必要な範囲を再検証する。
- マージ後は最新 main で検証し、完了した旧 Issue、PR、branch を整理する。
- 整理対象は不要になった branch、worktree、temp に限定する。未公開変更、他タスクの依存、必要な証拠を保護する。復元不能な削除等に必要な承認をこの契約で無効化しない。

## Phase の製品境界

ゲームルール、状態、秘密情報、transaction authority は Phase 内で一本化する。Sandbox semantic を保ち、Manual Resolution で進行を継続できるようにし、Correction を新しいゲームイベントにしない。actor、choice、Room、privacy の責務を分ける。既存 takeback を維持した上で、任意の strict knowledge-safe Undo を扱う。これらは製品境界の要求であり、古い OneDeck モック実装のコピー指示ではない。

## 改訂

各改訂で版、日付、変更理由、影響を記録する。通常の技術運営改善はラプラスくんが判断し、目的、体験、権限の範囲を広げる変更はユーザーに確認する。ユーザーの最新の明示方針を優先する。改訂履歴:

- 1.0 — 2026-09-30: 当日の合意と過去スレッドから確認できた運営原則を統合。指定スレッドは検索経由で全体を厳密に同定できていないため、確認できた会話断片とユーザー提供の要約だけを反映。
- 1.1 — 2026-09-30: 複数の境界不具合を扱う際、局所修正と上位契約案を全体の複雑さ・保守負担で比較し、証拠とともにオーナー判断へ渡す原則を追加。実装権限やゲームルール変更の許可は広げない。
